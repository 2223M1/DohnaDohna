# 从忍者杀手继承的开发路线

此文是经验提炼。Reference 中的历史文档可能早于代码，冲突时优先迁移来源 SHA 的实现与最新验证，再核对当前实际宿主 API。

## 从空骨架到第一版

1. 确定角色/玩法规格和稳定模型 ID，显示名后续可改。首版只做一个最小纵向切片：角色、初始牌组、一张卡、一项 Power、一件遗物、三语与一场实际战斗。
2. RitsuLib 注解注册内容，程序集在 Entry 注册发现；节点脚本、资源包、FMOD、Patch 均按出现的真实需求引入。
3. 编译真实宿主输入。两宿主独立编译/输出目录，禁止把同一 DLL 标成两版。改 Patch 时验证精确签名与回滚。
4. 先纯逻辑和仓库检查，再候选 DLL 契约与隔离游戏检查；最后多人、重载、取消和退出。不要为方便录制建立另一套玩法实现。
5. 从干净提交生成产物，记录源 SHA、DLL/PCK SHA256、宿主版本/MVID、实际 RitsuLib 版本、成功与未执行项。发布后重新下载逐文件比对。

## 卡牌与随机性

- 多段尽量一个原生 AttackCommand，使用原生整次攻击增益/活力语义；逐段重建命令会错误消耗活力。固定、随机和群攻的剩余段数语义不同。
- 抽牌只追本次直接抽到的实体；关联触发额外抽到的牌不能错误算入。满手、生成、复制、重复打出、升级与持久化分别验证。
- 随机目标使用持有者/战斗的原生随机流。显示、预览、悬停不消费随机数或活力，不造成伤害。
- 预见先等待原生抽弃/洗牌命令；确认按钮的鼠标释放不能穿透打开底层牌堆；牌堆数字须在原生实体移动后刷新。手动改数组/计数容易产生残留状态。
- 修改动态牌时尊重最终实例数值和关键词（如 Loadout），不要只读模型默认值。实例快照、衍生牌和本局状态明确分离。

## 战斗时序、处决与表现

- 伤害和动画命中同步。多段要等待最后一段、攻击回调和必要死亡/召唤处理；只有纯视觉收招可以解除玩家输入等待。
- 中间死亡会召唤/分裂时服从 Hook.ShouldStopCombatFromEnding，不能为处决把目标维持为假活体；后续目标让原生攻击命令处理。
- 守护者先决定替伤，再吸收真正落到玩家身上的伤害，最后判断致死。被其他 Mod 跳过的扣血不能记成真实受伤/死亡；复活或保命成功不能开启死亡处决。
- 个体冲刺/跳跃/击退只移动身体显示容器，保留原生根节点布局。整场镜头变换须同时作用于生物血条/状态栏和意图，但不移动真实队列、目标交互根节点或屏幕UI。恢复节点时尊重外部尺寸缩放；取消/重载后旧任务不能再覆盖新姿态。
- 投射物生成归属单次动作。影片只发释放时点，不能又由影片又由回退动画各结算一发。已发射后影片取消不可补发。
- 临时 UI、镜头、声音、挂接节点有明确取消与释放所有者。受击反击、死亡、战斗退出不能被无主后台 Task 吞掉异常。

## 联机与存档

- 友军沿用原生宠物/归属机制，站位修改不能变更真实玩家人数、敌人选人、奖励缩放或结束回合投票。
- 玩家选择通过原生同步流程，按持有者归属；不通过另建假玩家或额外自定义网络协议凑视觉位置。
- 非攻击、自伤、回合末损血死亡与怪物攻击死亡分别测试；一个玩家死亡后队友结束战斗必须能正常结算。
- 通过 RitsuLib 原生跑局持久化保存必要状态；显示计数直接读取真实 Power。保持序列化 ID 稳定，若有断代明确说明，不猜测迁移。
- 新局/读档/重连/快速 SL 都核对任务、输入锁、音乐和演出清理。加载性能要与原生过渡结束时点比较，不能仅因“比以前快”就宣称合格。

## 资源与外部生态

- Godot 引用统一 res://DohnaDohna，资源和源码分开；测试、工具、文档、参考、游戏依赖库不进入 PCK。
- 对原生 Spine 扩展只复用宿主，不将编辑器的 Windows 原生库打入跨平台运行包。FMOD bank/GUID/Event 来源一致并核对加载去重与音量。
- 可选模组的强类型引用隔离在可选程序集，缺少时不加载；不把其变成必需依赖。互操作优先官方 API，再在所属功能边界做精确 Patch。
- 后台可沿用最小权限、localhost 限制、附件校验、公开摘要/私有附件分离、反馈状态独立保存、失败保留输入及快照失败保留上次完整数据。新服务必须有新 KV/R2/域名和用户授权。
- 角色专属优化、处决、以太回流、猫粮杯种子、遥测等不是新项目默认功能。按明确设计挑选，不把工程经验理解成必须复制全部玩法。
